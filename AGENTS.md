# AGENTS.md

## Documentation

- Whenever a rule is added, removed, or changed in this file, re-review the whole file afterward and tighten it: merge overlapping or closely related bullets, cut redundant phrasing, and otherwise keep it as condensed as possible without dropping any distinct rule, example, or the reasoning behind a non-obvious rule.
- Documentation stays in sync with code: review and update the relevant `Docs/` file whenever you change behavior it describes. Keep docs as brief as possible without sacrificing essential details - a concise statement of what/why beats exhaustive narration. Docs describe only current behavior - update the relevant section in place rather than layering "used to be X, now Y" notes, since git history is where past behavior belongs.
- Do not add "See also" sections, or otherwise mention/link other doc files, from within a doc file.
- Do not restate code comments in doc files, and do not create tables enumerating types ("types at a glance") - that's what XML doc comments and IDE navigation are for; doc files explain design, flow, and rationale instead.
- New doc files for the design/implementation of a complex component go under `Docs/Components/`, one file per component - separate from the overall workspace documentation in `Docs/` root. A component is a related area of code or a concept, not necessarily a single type; group tightly coupled types together rather than creating one file per type.

## Coding

- File-scoped namespaces everywhere.
- Each project has a single `Using.cs` file containing all `global using` directives for that project. Do not place `using` directives in individual files.
- Each project restores with a committed `packages.lock.json` (`RestorePackagesWithLockFile`). After changing a `PackageReference`, run `dotnet restore` to keep the lock file in sync. Also update `THIRD-PARTY-NOTICES.txt` for any added, removed, or upgraded dependency (direct or transitive) whose resolved set or license changed - check its license expression (`dotnet list package` or its `.nuspec` in `~/.nuget/packages/<id>/<version>/`) rather than assuming it's unchanged.
- No comments unless the why is non-obvious - a hidden constraint, a platform quirk, a non-obvious invariant. Never comment what the code obviously does. No multi-line comment blocks, and no comments used to designate sections of members (e.g. `// ── Section ──` dividers) - order members by the rule below instead.
- All types and members (`public` and `internal`) require full XML documentation comments (`<summary>`, `<param>`, `<returns>`, `<exception>`, etc. as applicable). Use `<inheritdoc />` on members that implement a documented interface without adding meaningful additional documentation.
- `sealed` on all classes that are not designed for inheritance.
- Prefer `record` types with `required init` properties for DTOs and model types.
- `internal` by default; only `public` what a consuming application genuinely needs.
- One type per file, with these exceptions: an interface and its implementing class are co-located in one file named after the class (e.g. `IThing` and `Thing` both live in `Thing.cs`), unless the interface is public and the class internal: every internal type lives under `Internal/`, so the class goes in `Internal/Thing.cs` and the public interface stays in its own `Thing.cs` (the root or `Public/`), with the factory nested in the interface; extension classes are co-located with the class they extend (e.g. `ThingExtensions` also lives in `Thing.cs`); a standalone interface with no co-located implementation is named after its concept without the `I` prefix (e.g. `IOther` lives in `Other.cs`).
- Prefer extension types (`extension(Thing thing) { ... }` blocks) over classic `this`-parameter extension methods inside an extension class.
- Member ordering: group static members at the top of a type, then instance members below them. Within each group, order members by kind: constructors, fields, events, properties, operators, methods. Applies to interfaces too (events, then properties, then methods) - an interface's members are not exempt just because it has no constructors or fields.
- Always use braces for blocks - never an implicit one-line `if`/`else`/`for`/`foreach`/`while`/etc. Always write `if (...) { ... }`, never `if (...) ...`.
- Prefer expression-bodied members over full block bodies when possible and practical. For methods, put the `=>` on its own line, indented one level below the signature (`void Do()` then `    => Action();`), and indent anything the expression continues with (an initializer's braces, a `switch`'s arms) to match. For properties, the `=>` always stays on the same line as the signature (e.g. `public int Foo => value;`), even if the expression itself then needs to wrap onto following lines.
- For a property returning a reference-type value (list, array, dictionary, etc.), initialize its own backing field directly, once (e.g. `public IReadOnlyList<X> Foo { get; } = [5, 2, 3];`) - not an expression body that reconstructs it on every access, and not a separate `private static readonly` field just to hold it.
- Prefer instance over `static`: private instance fields over private static fields (even when the value is the same for every instance), and instance methods over `static` ones (even when a method touches no instance state) - reserve `static` for cases that genuinely require it (extension members, backing a static member, a genuine global access point like a service locator).
- Avoid `const` - a `const` value is baked directly into every call site at compile time rather than read at run time, a real versioning hazard the moment it's read from a different assembly (`Tests`, in this template), and it also carries its own special-cased PascalCase naming rule that a plain field or local variable doesn't need. Use a `static readonly` field for a fixed field-level value, and a plain (non-const) local variable for one scoped to a method body, even where the value would technically qualify as a compile-time constant. The only exceptions are places C# itself requires a genuine compile-time constant - a `switch`/`case` label, or an `is X or Y` constant pattern.
- No underscore prefix on private field names. Otherwise follow Microsoft's documented C# casing conventions: PascalCase for types, interfaces (with the customary `I` prefix), type parameters (with the customary `T` prefix), and every member regardless of accessibility; camelCase for parameters, local variables, and private fields, `const` included (per the rule above, `const` shouldn't come up - but if one is unavoidable, Microsoft's convention keeps it PascalCase at any accessibility level rather than following the plain-field camelCase rule, so a stray one doesn't silently drift out of sync with the rest of its own kind). `.editorconfig` enforces all of this mechanically.
- For private fields holding plain internal data (not an injected DI dependency), declare the field with its concrete/plain class type rather than an interface (e.g. `private readonly Dictionary<string, Widget> widgets = new();`, not `IReadOnlyDictionary<string, Widget>`; `private readonly List<string> names = [...];`, not `IReadOnlyList<string>`). This does not apply to DI-injected constructor/property dependencies, which continue to use their interface type per the DI convention.
- Prefer primary constructors when possible.
- Give every non-DTO class a corresponding `IThing` interface (co-located per the file-naming rule above); constructor and property injection always uses the interface type, never the concrete class.
- A type's factory is nested inside its primary public interface rather than declared as its own top-level type: `IThing.IFactory` and `IThing.Factory`, both declared inside `IThing`'s own file (`Thing.cs`) alongside `IThing` itself, even though `Factory.Create` constructs the internal `Thing` class from elsewhere. DI registration and construction then read as `IThing.IFactory`/`new IThing.Factory()`.
- Async all the way: write all I/O as async. Avoid `Task.Result` and `.GetAwaiter().GetResult()` except where a synchronization context deadlock is explicitly being avoided at a top-level entry point. Do not append `Async` to method names - name methods by what they do, not how they do it (`Send`, not `SendAsync`). Name `CancellationToken` parameters `cancellation` (not `ct` or `cancellationToken`) and make every one optional with `= default`, last in the parameter list, on interfaces, implementations and private methods alike; framework-required overrides are the only exception.
- Thread safety: use `SemaphoreSlim(1,1)` for async-compatible locking, `ConcurrentDictionary` for shared maps, `lock` for short synchronous critical sections.
- Byte spans over arrays: use `ReadOnlyMemory<byte>` / `ReadOnlySpan<byte>` for payload and data-chunk parameters and return types at method boundaries; use `Memory<byte>` when the callee needs to write. Reserve `byte[]` for internal read buffers allocated with `new byte[n]` and for interop with APIs that require it.
- No `var`: always declare the explicit type on local variables. Use C# 9+ target-typed `new()` to avoid repetition when the type is already on the left-hand side (e.g. `Widget widget = new();`). For tuple deconstructions write the types inline: `(string id, bool ok) = GetResult()`.
- Put new unit tests (no real I/O against external dependencies) in `Tests/src/Unit/`; integration tests (real I/O) in `Tests/src/Integration/`. Put shared test infrastructure directly under `Tests/src/`. Use xUnit; mock dependencies with Moq.

## Avalonia and CEF

- Keep Avalonia on the 11.3 line: `CefGlue.Next.Avalonia` is built against it and throws `TypeLoadException` (`GotFocusEventArgs`) on Avalonia 12. Only move up once the binding supports it, and update `THIRD-PARTY-NOTICES.txt` and the lock file with it.
- `Program.Main` runs `HelperProcess` first when it is started as a CEF helper (`--type=`), since this executable is also CEF's helper process; it replaces CefGlue's `CefSubProcess.Run` so that the renderer can run scripts at JavaScript context creation (`RendererScripts`) and must keep exiting when the browser process does. CEF itself is initialized by `CefStarter` in `AfterPlatformServicesSetup`: `AfterSetup` runs after `App.OnFrameworkInitializationCompleted`, by which point the first browser would already have initialized CEF with default settings.
- Keep `WindowlessRenderingEnabled` on. Windowed mode embeds a native X11 child window that receives keys before Avalonia whenever the pointer is over the page, and brings Chrome's own UI with it (native menus that never close, accelerators such as Ctrl+T opening native Chrome windows).
- Pages are always dark: the `force-dark-mode` and `WebContentsForceDark` switches plus the dark browser background color in `BrowserTab`. Keep all three.
- `AvaloniaCefBrowser` has no parameterless constructor, so `PageBrowser` is created in code (in `BrowserTab`) and hosted in a panel, not declared in XAML. It must stay `Focusable` and take focus on press, or CEF never gets keyboard focus and typing into page fields silently does nothing. It also pushes the cursor CEF asks for onto its visual descendants, because Avalonia does not inherit `Cursor` and the hit-tested element is a nested image.
- The profile lives in `LocalApplicationData/Markwardt.Browser` (`CefSettings.CachePath`, `PersistSessionCookies`) so sign-ins survive restarts. Chromium only writes cookies in delayed batches and not at all on this process's exit path, so `CookieStore` flushes every 15 seconds and `App` holds shutdown until a final flush completes. A profile cannot be shared, so only one process runs per user: `SingleInstance` makes a later launch hand its whole command line to the running copy over a named pipe and exit before CEF starts (otherwise CEF opens a native Chrome window in the first), and the running copy opens a new window for it. Launch options (`LaunchOptions`) belong to the window they create, not to the process: `App.CreateWindow` takes them, so a handed-over `--isolate` or `--close-only` affects only its own window.
- CEF raises its events and calls its handlers on its own threads, and passes `null` for empty strings (status message, menu labels, ...). Coalesce with `?? string.Empty`, and post to `Dispatcher.UIThread` before touching a control. An exception inside a CEF callback kills the process with a bare SIGSEGV; locate it with gdb plus `DOTNET_PerfMapEnabled=1`.
- Bookmarks (`BookmarkList`, saved by `BookmarkFile` as JSON in the profile folder) are saved fire-and-forget after every change; the save is serialized, atomic and swallows `IOException` and `UnauthorizedAccessException` so a bad disk never breaks the UI. `Load` merges with bookmarks added meanwhile. Pages are matched by address ignoring case. While a bookmark is being renamed, `MainWindow.OnWindowKeyDown` must leave keys to the rename field, or Esc would close the overview instead of cancelling the edit.
- The top bar (address box, navigation, window controls) shows outside the overview only while the user keeps it toggled on (`IUserSettings.TopBarVisible`, saved in `settings.json`, default on); otherwise the window is only the page and F1 raises the overview (tab cards, bookmark sidebar) with the bar over it. Beyond that there is no other persistent UI: do not add chrome back (tab strips, status bars). New features get a place inside the overview or the top bar, not elsewhere; the one exception is the transient find box (Ctrl+F), which floats over the page only while a search is active and closes when the overview opens or the tab changes. The address box uses one meaning throughout: `:` then an address loads in the active tab, anything else searches in a new tab; `IAddressResolver` (`Interpret`, `Describe`, `Resolve`) is the only place that knows it. Esc closes the bookmark suggestions before it closes the overview. With the bar visible outside the overview the address box also follows the page's address, reverts on Esc or lost focus, and Ctrl+L only focuses it. Moving focus between the page and the overview or address box needs both sides: `ReleaseFocus` plus `Activate` and `Focus` on the address box going in, and `Focus` on the page coming out, otherwise keys keep going to the wrong one.
- Hidden tabs do not render, so a tab's thumbnail is captured when it stops being active and when the overview opens; overlay images must be non-hit-testable (`IsHitTestVisible="False"`) or they swallow clicks meant for the controls under them.
- Keyboard shortcuts live in `ShortcutMap` (with the Windows virtual key CEF reports) and reach the window by two paths: Avalonia key events when the UI has focus, and `BrowserKeys` (CEF `OnPreKeyEvent`) when the page has focus. Add new ones to the map, not to either path. CEF `Char` events carry the typed character in the key code field (`p` is 112, the same as F1), so `ShortcutMap` ignores them; any new key interpretation must too.
- Page tooltips go through `BrowserTooltips`, which hands every text to `PageBrowser` instead of the CefGlue control: that control leaves the text on itself after closing, and Avalonia's tooltip service then shows it again whenever the pointer re-enters. `PageBrowser` shows a tooltip only while the pointer is over a visible page, clears the text whenever it closes (empty text from CEF, pointer exit or movement away, press, wheel, key, hidden tab), and non-empty ones are suppressed while a context menu is open and briefly after. Never suppress empty tooltips, which clear CefGlue's cached text.
- The context menu is built from CEF's menu model in `BrowserContextMenu`. CEF's menu callback must always complete: `Continue` on a choice, `Cancel` otherwise. Commands that would open native Chrome windows (view source) become tabs instead.
- Pressing a button makes the CefGlue control capture the pointer, which Avalonia reports as `PointerExited`, which CefGlue forwards as the mouse leaving the page (YouTube's hover preview then closes before the release and the click is lost). `PageBrowser` swallows an exit while it holds the capture; keep that. Middle click and Alt+click on a link are taken in `PageBrowser` (using the hovered link from CEF's status message) and swallowed, because Chromium would auto-scroll or download.
- Site-specific behavior and video mode are scripts run per frame after load (`Sites/`: `ISiteRule`, `VideoModeRule`, `YouTubeRule`, scripts embedded as `*.js` resources); add a site as a new rule, not as code in the tab or window. Window-level behavior stays in `App`: several `MainWindow`s share bookmarks and the profile and each owns its tabs.
- Ads are blocked in `Ads/` and wired through `BrowserRequests` (cancels requests; never page navigations), `BrowserPopups` (refuses gesture-less popups and ad popups) and `BrowserTab.HideAds` (per-frame cosmetic and YouTube script, run on load start and end). `FilterParser` skips any rule it cannot honor instead of approximating it: widening a rule breaks sites. Matching runs on CEF threads per request, so `AdBlocker` swaps an immutable `FilterSet` and rule lookup stays token-indexed (`NetworkRule.FindToken`); keep a lookup in the tens of microseconds. Only http, https, ws and wss addresses are filtered (`file:` test pages are not; serve them over a local HTTP server). Filter lists are downloaded by the user's copy into `filters/` in the profile, never bundled, so their licenses stay out of releases; `BuiltIn.txt` is the offline fallback. YouTube ads cannot be told apart by address: `YouTubeAds.js` strips ad fields from player data and skips ads that still play, and it only works if it runs before the page's own scripts, which a script sent from the browser process at load start does not (measured), so the renderer runs it when each frame's context is created. Ad networks rotate domains, so `BuiltIn.txt` also carries rules for the shape of ad requests (VAST); lists are widened only with ad lists, not tracking lists (EasyPrivacy breaks sites). `--stats` writes the blocker's decisions to `requests-*.log` for finding leaks.
- Types the framework or CEF constructs (`Program`, `App`, `MainWindow` and other views, `PageBrowser`, CEF handler subclasses) are exempt from the interface-per-class rule.
- A published build is one executable with the CEF runtime zipped into it (`PackCefRuntime` in `App.csproj`, only when publishing; `-p:CefRuntimeFolder=<folder>` replaces the files, as `Scripts/Install.cs` does with the codec runtime), because `libcef` cannot load from the .NET single-file bundle. `CefRuntimeFolder` unpacks it once into `Markwardt.Browser.Runtime/<hash>` and must run (`Prepare`, `Activate`) before `CefSubProcess.Run` in every process, helpers included, since they are the same executable. `Activate` sets the working directory to the unpacked folder and registers a resolver for `libcef`: CefGlue only looks beside the executable and in the working directory, then scans the folders above it, which can mean the user's whole home folder. Publishing also compiles ahead of time (`PublishReadyToRun`, publish only; it halves the time to the first window), while plain builds are not precompiled and keep the runtime loose beside the executable. Performance work is measured, not assumed: before trying a Chromium flag, GC setting or input-path override again, check what `Docs/Components/Performance.md` already measured (most had no effect). Keep `CefRuntimeVersion` in `App.csproj` equal to the CEF package version. Releases are still a zip per platform (the executable plus notices) so the Linux file keeps its executable bit; the Windows runtime packing is built but could not be run on the development machine.
- Test the UI headlessly under `xvfb-run` with `openbox` running (bare Xvfb has no input focus handling; give it a config with empty `<keyboard/>` and `<mouse/>` sections, or it grabs Alt+click for window moves) and `xdotool` for input, never on the real display. Find the window by PID, not by name: the window title follows the page title. Always isolate a test copy from the user's own running browser: the app is single-instance per user, so a test launch otherwise hands its command line to the user's real copy (opening a window in it) and exits. Set `TMPDIR` (holds the single-instance pipe) and `XDG_DATA_HOME` (holds the profile, bookmarks and settings) to scratch folders inside the script that launches the app; exporting them from the calling shell is not reliably inherited. Command line options (each applies to the window its launch opens): `--goto <url>` (go straight to the page, no overview), `--isolate` (no overview, top bar always on with only the window controls, nothing saved), `--window maximized|unmaximized|minimized`, `--close-only` (minimize and maximize hidden), `--stats` (performance log in `stats/` of the profile, process-wide: only the launch that starts the browser decides it; `Scripts/Install.cs -- --stats` puts it in the launcher entry); `LaunchParser` is the only place that reads them, and `--isolate` also makes new-tab requests load in the current tab, since tabs cannot be switched.
- GPU: CefGlue's off-screen mode normally hard-codes `--disable-gpu` and `--disable-gpu-compositing`, so `CefStarter` bypasses its loader (flipping the internal `CefRuntimeLoader.IsOSREnabled` by reflection) and initializes CEF with `BrowserApp`, which adds only `--no-zygote` and `--enable-begin-frame-scheduling` (its `--disable-smooth-scrolling` is dropped, and `BrowserTab` asks for 60 fps, so wheel scrolling animates). Chromium chooses its own graphics backend: `--use-angle=vulkan` was tried and must not be the default, because on the NVIDIA machine it loses the Vulkan device (`VK_ERROR_DEVICE_LOST`) and fails to import video frames from DMA-BUFs, which crashes the GPU process repeatedly (the page freezes, repaints, and hover preview videos do not play). Vulkan is an opt-in for headless testing only (`MARKWARDT_ANGLE=vulkan`, via `ChromiumSwitches`): the GPU process cannot boot on Xvfb through Chromium's default backend, so a headless run without it has no GPU or WebGL, and a real display is the only place the default can be checked (`--stats` records `gpu-restarts` and the header says what was asked, and the profile's `chrome_debug.log` has Chromium's own errors). `ChildProcessHandler` passes `--parent-pid` so helpers exit with the app. The Avalonia control still copies each finished frame from CPU memory (it does not use CEF's shared-texture paint). NuGet's CEF lacks proprietary codecs, so H.264, AAC and HEVC do not play, and neither do AV1 or VP9 streams that carry AAC (Steam trailers show "Video format not supported"). `Scripts/Codecs.cs`, run by `Install.cs` (as the runtime to pack) and `Run.cs` (over the build output), provides a community build of the same Chromium version with `proprietary_codecs=true` (pinned URL and SHA-256, Linux x64 only); when the CEF package version changes, update its URL, hash and archive root to a matching build or drop the overlay. The release workflow does not apply it. HEVC needs hardware decoding and stays unsupported. Check the result with `chrome://gpu` and a WebGL renderer string, headlessly as below.

## Verification

- After every change, before reporting it done, run from the repository root, in order, and fix whatever fails: `dotnet format`; `dotnet tool restore`; `dotnet build`; `dotnet test Tests/Tests.csproj --configuration Debug --settings Tests/coverage.runsettings --collect:"XPlat Code Coverage" --results-directory Tests/TestResults`; then `dotnet tool run reportgenerator -reports:"Tests/TestResults/**/coverage.cobertura.xml" -targetdir:.github/badges -reporttypes:Badges` to regenerate the coverage badge, and finally delete `Tests/TestResults/`. Leave any formatting or badge changes for the user to review and commit. CI (`build.yml`) only checks the same things (a locked-mode build, `dotnet format --verify-no-changes` and the tests) and never fixes or commits, so these steps are what keep it green.
